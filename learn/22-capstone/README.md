# 里程碑 22：毕业项目——闭卷重写 mini-pi

> 目标：合上教程，从一个空目录开始，不借助 AI，写出一个能通过验收测试的 mini-pi。
>
> 这是整门课的终点。前面每一章最后都有一个"闭卷挑战"，这一章把它们连在一起：不是重写某一个函数，而是重写整个程序。能做到这一点，你就真正把 coding agent 吃透了。

## 你将证明

- 你能从零搭起 coding agent 的每一层：模型接口、agent loop、工具、会话、终端界面
- 你能只靠官方文档和报错信息解决问题
- 你理解每一个设计决定，因为你要重新做一遍这些决定

---

## 1. 规则

**不能看：**

- 这门课的正文和参考答案（`learn/*/README.md`、`learn/*/code/`）
- pi 的源码
- 任何 AI：聊天机器人、编辑器里的 AI 补全（GitHub Copilot、Cursor 的 Tab 补全……先在设置里关掉）
- 你以前在 `~/my-pi` 里写的代码

**可以看：**

- 这一章（`learn/22-capstone/README.md`）和验收测试 `learn/22-capstone/check.test.ts`：它们就是"需求文档"
- [假模型服务器](../tools/fake-llm/README.md)的说明：它是你的测试工具
- 官方文档：[Node.js](https://nodejs.org/docs/latest/api/)、[MDN](https://developer.mozilla.org/zh-CN/)、[TypeScript 手册](https://www.typescriptlang.org/docs/handbook/intro.html)、[OpenAI Chat Completions](https://platform.openai.com/docs/api-reference/chat)、[Anthropic Messages](https://docs.anthropic.com/en/api/messages)、各家服务商的 API 文档
- 你自己手写的**概念笔记**（不是代码）

**其他要求：**

- 新建一个空目录，比如 `~/mini-pi-final`，用 git 管理，经常提交。
- 零运行时依赖：只用 Node.js 的内置模块。`devDependencies` 里只允许 `typescript` 和 `@types/node`。
- 不限时间。建议记一份工作日志（比如 `LOG.md`）：每天做了什么、在哪里卡住了、查了什么。做完回头看，这份日志就是你最真实的成长记录。

### 卡住了怎么办

按顺序来，每一步都试过了再走下一步：

1. 读报错信息：错误类型、文件、行号。
2. 打印：在怀疑的地方 `console.log`，看实际的值。
3. 写一个最小的实验：新建一个 10 行的小文件，只验证你不确定的那一个点（比如"`TextDecoder` 遇到半个汉字会怎样"）。
4. 查官方文档。
5. 休息一下，第二天再看。很多问题睡一觉就想通了。
6. 卡住超过一天：可以打开**对应那一章的"接口约定与测试"一节**（只看这一节，不看代码），并在日志里记下来。全部做完之后，把这些章节的闭卷挑战重新做一遍。

查过资料不丢人。目标是学会，不是考满分。

## 2. 要做出什么：接口规范

验收测试像用户一样从命令行运行你的程序：启动一个假模型服务器，在一个临时目录里运行 `node <你的项目>/src/cli.ts ...`，然后检查程序的输出、磁盘上的文件，以及**你的程序发给模型的请求**。它不关心你的代码怎么组织，只要求下面这些行为。

### 2.1 项目

- 入口是 `src/cli.ts`，用 `node src/cli.ts` 运行。
- `package.json` 里有 `"type": "module"` 和 `version`。
- 工作目录就是运行程序时的当前目录（`process.cwd()`）。
- 数据目录：环境变量 `MINI_PI_DIR`，没有设置时是 `~/.mini-pi`。全局的 `AGENTS.md`、`settings.json`、会话文件都放在这里。

代码怎么分目录由你决定。参考：`src/ai/`、`src/agent/`、`src/tools/`、`src/core/`、`src/modes/`、`src/tui/`。

### 2.2 连接模型

`--model <服务商>/<模型名>` 选择模型。验收测试只用一个服务商 `custom`，它从环境变量读取配置：

| 环境变量 | 含义 |
| --- | --- |
| `LLM_BASE_URL` | 服务地址 |
| `LLM_API_KEY` | API key |
| `LLM_API` | 协议：`openai-completions`（默认）或 `anthropic-messages` |

| 协议 | 请求 | 认证 | 测试里的 `LLM_BASE_URL` |
| --- | --- | --- | --- |
| `openai-completions` | `POST ${LLM_BASE_URL}/chat/completions` | `Authorization: Bearer <key>` | `http://127.0.0.1:端口/v1` |
| `anthropic-messages` | `POST ${LLM_BASE_URL}/v1/messages` | `x-api-key: <key>` 和 `anthropic-version: 2023-06-01` | `http://127.0.0.1:端口` |

要求：

- 用流式（`"stream": true`）。服务器发来的数据可能被切成任意大小的碎片，一行、甚至一个汉字都可能被切成两半。
- 思考过程（OpenAI 协议里的 `reasoning_content`，Anthropic 协议里的 `thinking`）要能接收，但 print 模式不输出它。
- 模型返回 HTTP 错误时，错误信息里要有状态码和服务器给的说明，比如 `HTTP 401：Invalid API key`。

真实的服务商（DeepSeek、通义千问、Anthropic……）不在验收测试里，但你肯定想接上一个真正的模型试试。

### 2.3 命令行

验收测试用到的选项：

| 选项 | 作用 |
| --- | --- |
| `-p`, `--print` | 非交互模式：处理完消息，输出最终回答，退出 |
| `-m`, `--model <服务商/模型>` | 选择模型 |
| `-t`, `--tools <名字,名字>` | 只启用这些工具，比如 `read,ls` |
| `--no-tools` | 不启用任何工具（请求里不带工具） |
| `-c`, `--continue` | 继续当前目录最近的会话 |
| `--no-session` | 不保存会话 |
| `-h`, `--help` | 输出用法（要提到 `--model` 和 `-p`），退出码 0 |
| `-v`, `--version` | 输出版本号（形如 `1.0.0`），退出码 0 |
| `@文件` | 文件的内容附加到第一条消息里 |
| 其他参数 | 要发送的消息 |

不认识的选项：在标准错误（stderr）里说明，退出码 1。

### 2.4 print 模式

```bash
mini-pi -p "你是谁"
cat error.log | mini-pi -p @src/main.ts "解释一下"
```

- **标准输出（stdout）只有最终的回答**：最后一条助手消息的文字，后面跟一个换行。思考过程、工具调用的过程、提示信息都不能出现在 stdout 里（需要的话写到 stderr）。
- 成功时退出码 0。最后一条助手消息是错误时：把错误信息写到 stderr，退出码 1。
- 标准输入不是终端时（被管道连接），读取它的全部内容。内容不为空的话，和 `@文件` 的内容、第一条消息合成**第一条用户消息**。测试运行你的程序时，标准输入总是一个管道：没有内容时它会马上关闭，你的程序不能卡在那里等。

### 2.5 系统提示词

请求里的系统提示词必须包含：

1. 工作目录的完整路径；
2. 可用的工具（至少要有名字）；
3. 全局的 `$MINI_PI_DIR/AGENTS.md` 和工作目录里的 `AGENTS.md` 的内容，**全局的在前**（项目的规则更具体，放在后面，模型更容易优先遵守）。

### 2.6 五个工具

| 工具 | 参数 | 行为 |
| --- | --- | --- |
| `read` | `path`（必填）、`offset`、`limit` | 读取文本文件。`offset` 是从第几行开始（第一行是 1），`limit` 是最多读几行。输出超过 **2000 行或 50KB** 时只返回前面的部分，并提示怎样继续读，提示里要出现 `offset`，比如 `[还有 3000 行。用 offset=2001 继续读取。]` |
| `write` | `path`、`content`（都必填） | 写入文件，覆盖原来的内容。目录不存在时自动创建 |
| `edit` | `path`、`edits`（都必填） | `edits` 是一个数组，每一项是 `{ oldText, newText }`：把 `oldText` 替换成 `newText`。每个 `oldText` 都必须在文件里**正好出现一次**；有任何一项找不到或者出现了多次，就报错，文件保持不变。错误信息里要提到文件路径 |
| `bash` | `command`（必填）、`timeout`（秒，可选） | 在工作目录里执行命令。结果包含标准输出和标准错误。退出码不是 0 时，结果里要说明退出码。输出超过 2000 行或 50KB 时**只保留最后的部分**（错误信息一般在最后） |
| `ls` | `path`（可选，默认 `.`） | 列出目录里的文件和子目录，按名字排序，目录名后面加 `/` |

相对路径都相对于工作目录。工具的参数用 JSON Schema 描述，属性名必须和上表一致（测试会检查请求里的工具定义）。

出错时的规则（agent loop 的规则）：

- 工具执行出错、参数不对（比如缺少必填参数）、模型调用了不存在的工具：**都不能让程序崩溃**。把错误信息作为工具结果告诉模型，让它自己改正，agent 继续运行。
- 参数错误的信息里要提到出错的参数名（比如 `content：缺少必填参数`），不存在的工具要提到工具名。
- 模型在一次回复里调用了多个工具时：可以同时执行，但工具结果要**按调用的顺序**放回对话里。

### 2.7 会话

- 默认保存每一次对话，存成 JSONL 文件（每行一个 JSON），放在 `$MINI_PI_DIR` 下面（具体的子目录和文件名由你决定，测试会在整个 `$MINI_PI_DIR` 里找 `.jsonl` 文件）。
- `-c`：找到**当前目录**最近的会话，把旧的对话发给模型，新的消息追加到**同一个文件**里。
- `--no-session`：不创建会话文件。

### 2.8 自动重试和设置文件

- 读取 `$MINI_PI_DIR/settings.json`（文件可以不存在）。至少支持：

  ```json
  { "retry": { "enabled": true, "maxRetries": 3, "baseDelayMs": 2000 } }
  ```

  只写了一部分的设置，其他的用默认值（上面就是默认值）。
- 临时性的错误自动重试：HTTP 429（请求太频繁）、5xx（服务器出错、太忙）、网络错误。等待时间是 `baseDelayMs`、`2 × baseDelayMs`、`4 × baseDelayMs`……
- 不重试：401（API key 不对）、400（请求不对）、额度用完了。
- 重试成功之后，程序照常输出，就像什么都没发生过。

验收测试把 `baseDelayMs` 设成 10 毫秒，免得等太久。如果你还没有读取设置文件，这个测试也能通过，只是要多等 6 秒。

### 2.9 不在验收测试里，但属于 mini-pi v1.0

下面这些没法用命令行测试自动检查，用第 5 节的手动清单检查：

- 交互模式：差分渲染的终端界面、多行编辑器、Markdown 渲染、工具执行的显示、底部的状态栏
- Esc 打断、运行中插话（steering）、排队的消息（follow-up）
- 危险命令执行前确认
- 上下文压缩（自动和手动 `/compact`），上下文超出上限时的恢复
- 斜杠命令：`/help`、`/model`、`/session`、`/settings`……
- 更多的服务商和模型表

## 3. 运行验收测试

在课程仓库的根目录运行：

```bash
MY_PI=~/mini-pi-final node --test learn/22-capstone/check.test.ts
```

先不设置 `MY_PI` 运行一次。这时检查的是参考答案（里程碑 20），23 个测试应该全部通过。这一步确认你的环境没有问题：

```bash
node --test learn/22-capstone/check.test.ts
```

刚开始时大部分测试都会失败，这很正常。只运行名字里包含某些文字的测试：

```bash
MY_PI=~/mini-pi-final node --test --test-name-pattern="print 模式" learn/22-capstone/check.test.ts
```

测试失败时，先看断言的说明（比如"思考过程不输出"），再看你的程序的 stderr。想知道你的程序到底发了什么请求，可以单独启动假模型服务器，加上 `--verbose`，然后手动运行你的程序：

```bash
node learn/tools/fake-llm/server.ts --verbose
LLM_BASE_URL=http://localhost:4000/v1 LLM_API_KEY=fake node src/cli.ts --model custom/fake-model -p "读取 package.json"
```

每次运行你的程序最多等 15 秒，超时会算作失败。

## 4. 推荐的路线

不要一口气写完再测试。按下面的顺序，每完成一个阶段，就多通过几个测试。括号里是**累计**通过的测试数。

| 阶段 | 要写的东西 | 新通过的测试 |
| --- | --- | --- |
| 1. 骨架 | `package.json`、`tsconfig.json`、`src/cli.ts`：解析参数，`--help`、`--version` | `--version`、不认识的选项（2） |
| 2. 和模型说话 | 消息和事件的类型、事件流、SSE 解析、OpenAI 适配器、`custom` 服务商、print 模式 | print 模式、碎片、不可重试的错误（5） |
| 3. Agent 和工具 | 工具的类型、参数校验、agent loop、Agent 类、五个工具、截断、`--tools` | 工具定义、`--tools`，以及所有的工具测试（18） |
| 4. 系统提示词和输入 | 读取 `AGENTS.md`、组装系统提示词、管道输入、`@文件` | 系统提示词、管道输入（20） |
| 5. 第二种协议 | Anthropic 适配器 | Anthropic 协议（21） |
| 6. 会话 | JSONL 会话文件、`-c`、`--no-session` | 会话（22） |
| 7. 重试和设置 | 设置文件、可重试的错误、指数退避、`Agent.continue()` | 自动重试（23） |
| 8. 上下文压缩 | 估算 token、找切分点、生成总结、自动压缩 | 手动检查 |
| 9. 终端界面 | 终端、按键、字符宽度、差分渲染、编辑器、Markdown、交互模式 | 手动检查 |

几点建议：

- **每个阶段先写测试**（至少是最重要的几个），再写代码。验收测试只从外面看；你自己的单元测试能告诉你问题出在哪个函数里。
- **阶段 2 和阶段 3 是心脏**。第一次跑通"模型调用工具、工具返回结果、模型给出回答"时，花点时间单独体会一下：整个 coding agent 的核心就是这个循环。
- **阶段 9 是最大的一块**，一个人从零写出一个不闪烁的终端界面并不容易。可以先用 `node:readline` 写一个简单的逐行模式凑合着用，等其他部分都稳定了再写。
- 第一次写不出最好的结构没关系。全部通过之后，回头重构：哪里重复了？哪个文件太长了？有测试保护，重构不用怕。

## 5. 手动检查清单

验收测试全部通过之后，用真正的终端和真正的模型逐项检查：

**基本功能**

- [ ] 不带 `-p` 启动，进入交互界面；回答逐字流式显示
- [ ] 让它完成一个真实的小任务，比如"给这个项目加一个 `--verbose` 参数，然后运行测试"
- [ ] 工具调用的过程清楚：调用了什么、参数是什么、结果（太长时折叠）
- [ ] 底部的状态栏：工作目录、模型、token 用量

**终端界面**

- [ ] 长回答不闪烁；向上滚动能看到之前的内容
- [ ] 改变窗口的宽度：内容重新排版，不会乱
- [ ] 中文输入法：候选词窗口跟着光标
- [ ] 多行输入：能用快捷键换行（比如 Ctrl+J），方向键在行之间移动，长的行自动折行
- [ ] 中文、emoji 的宽度正确，光标位置不会错位
- [ ] 代码块、列表、表格的 Markdown 渲染

**控制**

- [ ] 运行中按 Esc：停止；排队的消息回到输入框
- [ ] 运行中输入消息并回车：模型在下一步看到它（插话）
- [ ] 执行 `rm -rf` 之类的命令之前先问你
- [ ] 按两次 Ctrl+C 退出；退出后终端恢复正常（光标、回显、换行都正常）

**记忆和可靠性**

- [ ] 退出后 `-c` 继续，模型记得之前的对话
- [ ] 长对话自动压缩（用 `--context-window 8000` 之类的小数字试验）；压缩之后模型还记得任务
- [ ] 断开网络发一条消息：自动重试，等待时可以按 Esc 取消
- [ ] 设置文件写错一个名字：启动时有提示
- [ ] `/model` 切换模型，`/help` 列出所有命令

## 6. 自我评估

| 等级 | 标准 |
| --- | --- |
| 合格 | 23 个验收测试全部通过；用真实的模型完成了一个小任务 |
| 良好 | 合格，并且：有交互界面（差分渲染、多行输入、Esc 打断）、会话和上下文压缩 |
| 优秀 | 良好，并且：手动清单全部通过；你的项目有自己的单元测试；`tsc` 没有错误；能回答下面所有的问题 |

**讲给别人听**是最好的检验。合上电脑，在纸上或者白板上回答这些问题，假装在给一个刚入门的朋友讲：

1. 画出 agent loop 的流程图。循环什么时候结束？
2. 工具执行出错时，为什么要把错误作为结果告诉模型，而不是抛出异常、让程序停下来？
3. SSE 的一行被切成了两半，一个汉字被切成了两半，你的程序分别怎么处理？
4. 为什么 `edit` 要求 `oldText` 在文件里只出现一次？为什么不用行号来定位？
5. `bash` 的输出为什么保留最后的部分，而 `read` 保留前面的部分？
6. 为什么会话文件用 JSONL，而不是一个大的 JSON？
7. 压缩上下文时，为什么不能从一个工具调用和它的结果中间切开？
8. 屏幕上只有第 3 行变了，差分渲染向终端输出了什么？
9. 用户在模型执行工具时插话，消息什么时候送到模型那里？为什么不马上送？
10. 服务器返回 429，什么时候应该重试，什么时候不应该？

每个问题都对应课程的一章。讲不清楚的，回到那一章，把闭卷挑战再做一遍。

## 7. 毕业之后：延伸挑战

mini-pi v1.0 只是一个起点。下面这些功能 pi 都有，挑你感兴趣的做，每一个都是一次新的学习：

| 挑战 | 提示 |
| --- | --- |
| 会话树 | 会话文件里每条记录都有 `parentId`。实现 `/fork`：从某一条消息分出一个新的分支；`/tree`：浏览和切换分支 |
| 思考强度 | `off`、`low`、`medium`、`high`，分别对应各家服务商不同的参数（OpenAI 的 `reasoning_effort`、Anthropic 的 `thinking`） |
| 技能（skills） | 一个目录里放着很多说明文件，系统提示词里只列出名字和简介，模型需要时自己用 `read` 读取 |
| 扩展 | 启动时加载 `~/.mini-pi/extensions/*.ts`，让它们注册命令、工具，监听 `tool_call` 事件（参考里程碑 21 的第 7 节） |
| 图片 | 用户输入图片的路径，把图片发给支持视觉的模型 |
| 第三种协议 | OpenAI 的 Responses API，或者 Google Gemini |
| MCP | 实现一个 MCP 客户端：启动一个外部的工具服务器，用 JSON-RPC 和它通信，把它的工具交给模型 |
| RPC 模式 | 用标准输入输出上的 JSON 行和其他程序通信，让编辑器插件可以控制 mini-pi |
| 给 pi 贡献代码 | 读 [CONTRIBUTING.md](../../CONTRIBUTING.md)，从一个小 issue 开始 |

## 8. 结束语

回想一下里程碑 00：你还不知道终端是什么，第一次运行 `node --version`。

现在你写出了一个能读写文件、执行命令、记住对话、在终端里流畅交互的 coding agent。HTTP 请求、流式解析、参数校验、终端渲染，全是你自己的代码。更重要的是，你知道它们**为什么**是这个样子。

用 AI 写代码的时代，这份理解更有价值：你知道 coding agent 能做什么、不能做什么，它出错时你知道去哪里找原因，你能判断它写的代码对不对。你不再只是一个使用者。

祝贺你毕业。
